# 两个 agent 共用一个工作区，一定会互删

这不是假想。一个下午之内，双向都发生了。

## 事故记录

**方向一：范围删除吃掉了三个函数。**

一个会话在 `device/components/ui/diagnostics_ui.cpp` 里留了临时探针，清理时用了"从标记注释删到某个已知符号"的整段替换：

```python
start = s.index("\n// TEMPORARY: locating the horizontal seam")
end   = s.index("static lv_draw_buf_t* decode_still(const char* path) {")
s = s[:start] + "\n" + s[end:]
```

而在这期间，另一个会话往这个区间里加了 `decode_jpeg_scaled`、`decode_still_full`、`shrink_still` 三个函数。它们从未提交过，所以 git 完全恢复不了。唯一还能捞到的，是上一次成功编译留下的目标文件里的函数签名：

```sh
xtensa-esp32s3-elf-nm build/esp-idf/ui/CMakeFiles/__idf_ui.dir/diagnostics_ui.cpp.obj
```

**方向二：整体重写 lock 文件，丢了一条记录。**

另一个会话为了加一条 `lvgl` 的 patch 记录，把 `device/deps.lock.json` 按自己内存里的旧副本整个重写了一遍。那份副本比几分钟前刚加进去的 `BMI270_BMM150_Sensor` patch 记录要早，于是那条记录没了，patch 文件也跟着被删。vendor 里的源码改动倒是还在——所以**本地看着一切正常**，要等到别人干净 checkout 才会炸。

**另外还撞到一次：** 编译报错说某几个函数未定义，可那几个函数在文件里明明白白写着。原因是编译器读到了写了一半的文件。重新编译一次就好了。

## 规矩

**优先用锚定的最小改动。** 替换一段你确切知道内容的字符串。**绝不要删除一段你没有刚刚完整读过的字节范围。**

**别拿内存里的旧副本整体重写文件。** 对 lock 文件、生成文件、清单文件尤其如此——恰恰是这类文件会被多条工作线同时碰。

**往结构化文件里插东西，用定点替换。** 给 `deps.lock.json` 加一个键，应该是一次锚定替换，不是 JSON 解析再全量序列化回去。

**早点提交。** 没提交的东西没有任何恢复路径。上面那三个函数救不回来，纯粹是因为它们从来没进过 git。

**一批改动前后都查一遍 `git status` 和 `git log`。** 那次会话里 `HEAD` 动了六次，文件状态在脚底下悄悄变。你开始时显示为已修改的文件，等你写完可能已经被别人提交了。

**编译失败可能是竞态，不是 bug。** 编译器报了不可能的错，先重新编一次再去查。

**把别人的东西弄坏了，立刻说。** 对方会话可能还在上下文里存着那段内容，能原样重新吐出来；靠签名重建出来的东西严格来说更差。而这个窗口是会关闭的。

## 更好的办法是别共用工作区

按目录分工，或者给每个会话开独立的 git worktree。上面这些规矩只能降低事故率，并不能让并发的整文件编辑变得安全。
